# Участие в EDT-Bridge

Спасибо за интерес. EDT-Bridge – это плагин для 1C:EDT плюс небольшая обвязка на Python. Здесь
описаны сборка, соглашения и порядок, в котором предлагают изменения.

## Базовые правила

- **Clean-room.** EDT-Bridge – независимая реализация, написанная с нуля, об этом говорит
  [ORIGIN.md](../../ORIGIN.md). Присылайте только собственный код, построенный на открытой
  спецификации MCP и публичных API плагинов Eclipse и 1C:EDT (`org.eclipse.*`,
  `com._1c.g5.v8.dt.*`). Не вставляйте декомпилированный или иной проприетарный код из EDT или
  другого инструмента.
- **Область.** Плагин отдаёт по MCP *живую* модель EDT. Новому инструменту должно быть нужно то,
  чего не даёт статический парсер: валидация работающей среды, настоящие типы, семантические ссылки,
  штатный рефакторинг, сборка. Если нет, инструменту лучше жить отдельно от моста.
- **Лицензия.** Присылая вклад, вы соглашаетесь, что он лицензируется под
  [Apache-2.0](../../LICENSE), inbound равно outbound.

## Сборка

Нужны **JDK под вашу EDT** и локальный **пул бандлов 1C:EDT**. Плагин компилируется против
собственных бандлов EDT, а они проприетарны и берутся из вашей локальной установки, поэтому сборки
через сеть нет. С EDT 2026.2 эти бандлы – class-файлы Java 25, и читать их умеет только JDK 25.
Скрипт определяет уровень по пулу и сам подхватывает более новый JDK, в том числе установленный
вместе с EDT. Байткод самого jar по-прежнему нацелен на Java 17.

```powershell
# Windows – по умолчанию: -Pool %USERPROFILE%\.p2\pool\plugins, -JdkHome %JAVA_HOME% (сам сменится, если старый)
powershell -ExecutionPolicy Bypass -File scripts/build-nomaven.ps1
```

```bash
# macOS / Linux – --pool определяется автоматически из установленного компонента 1C:EDT
./scripts/build-nomaven.sh
```

Jar кладётся в `build/`. Для полной сборки есть Maven и Tycho (`mvn -f pom.xml clean verify`), но
сначала отредактируйте `edt-bridge.target`. Подробнее: [README](README.ru.md#сборка-из-исходников).

## Запуск своей сборки

Скопируйте собранный jar в `dropins/` EDT и перезапустите EDT либо дайте это сделать обвязке.
Держите там ровно один jar EDT-Bridge: при двух Equinox возьмёт произвольный. MCP-сервер поднимается
на `http://127.0.0.1:8770/mcp`, а страница на `http://127.0.0.1:8770/` умеет запускать любой
инструмент. См. [Установку вручную](README.ru.md#установка-вручную-без-обвязки).

## Проверка изменения

Офлайн-набора тестов для Java-плагина нет. Он проверяется против **живой EDT**: собрать, положить в
`dropins/`, перезапустить EDT и запустить затронутые инструменты – со страницы в браузере или из
MCP-клиента. У инструментов записи сначала посмотрите план с `apply=false`, а потом уже `apply=true`.
Исполнитель GitHub так не умеет: для компиляции бандла нужны проприетарные бандлы 1C:EDT SDK. По той
же причине jar собирается локально и коммитится в `dist/`.

С обвязкой на Python иначе: она не зависит от EDT, поэтому у неё есть набор тестов pytest.

```sh
cd python
python -m pip install .[test]
python -m pytest -q
```

Сценарий `ci` запускает этот набор на каждый push и pull request – на Linux и Windows, на 3.10 и
3.12. Оба релизных сценария сначала вызывают `ci`, поэтому красный набор останавливает релиз, а не
выпускается мимо него. Windows в матрице не для красоты: единственный релиз, уехавший сломанным,
сломала ошибка кодировки, которая проявляется только там.

Новое поведение обвязки ожидается вместе с тестом, а исправленная ошибка – вместе с тестом, который
её воспроизводит. Из таких тестов набор в основном и состоит.

Часть плагина тоже покрывается тестами. Всё в `...edtbridge.core` – это чистая работа со строками:
где лежат исходники объекта, относится ли проблема валидации к тому, о чём спросили. Этот пакет
намеренно свободен от типов EDT и Eclipse, поэтому компилируется обычным JDK.

```sh
scripts/test-java.sh
```

Скрипт не кладёт в classpath ничего, кроме JUnit. Поэтому зависимость от SDK, просочившаяся в
`core`, ломает сборку, а не делает набор незапускаемым втихую. Логика, которой нужна живая модель,
остаётся в гейтвеях `...edtbridge.edt` и проверяется против настоящей EDT, как описано выше.

### Документация

`python scripts/check_docs.py` сверяет страницы с исходниками. У каждого инструмента и каждой
переменной `EDT_BRIDGE_` должна быть строка, блоки-зеркала в README – совпадать со
страницей-источником, а картинки – лежать в репозитории. Тот же скрипт запускает набор тестов
обвязки, поэтому разъехавшаяся страница роняет `ci` вместе с тестами.

Русские страницы он читает ещё и на слова. Словарь транслитераций лежит в общем
[docsguard](https://github.com/keyfire/docsguard), и с каждой находкой приходит русское слово
взамен. Слово, которое текст цитирует как слово, пишется в обратных кавычках – так запись журнала
называет заменённую транслитерацию, а проверка такие кавычки пропускает.

Тем же словарём читаются русские строки `python/src/edt_bridge_mcp/i18n.py`. Это каталог сообщений,
из которого берётся каждая строка `--help`. Названный файл, которого нет на месте, – тоже находка:
иначе после переименования каталога проверка прошла бы, не прочитав ничего.

`docs/changelog*.md` и `docs/onboarding*.md` – зеркала корневых документов. Пересобирает их
`node scripts/sync-docs.mjs`, а правят при этом источник.

### Запуск процесса

Процесс, запущенный из обвязки или из скрипта, читается как текст, и текст декодируется явно:
`capture_output=True, text=True, encoding="utf-8"`, плюс `errors="replace"` там, где вывод идёт
человеку. Без `encoding` Python декодирует кодовой страницей машины, и отказ выходит молчаливым
худшим образом. Вывод возвращается символами замены либо декодирование падает внутри потока чтения и
оставляет вывод пустым, а код возврата продолжает говорить, что всё прошло хорошо. Именно так
перестал срабатывать сторож, отказывающий в запуске headless, пока рабочую область держит EDT с
интерфейсом. Вызову, который вовсе не просит текста, не нужно ни то, ни другое: байты на входе,
байты на выходе, декодирование руками потом, как сделано в опросе через `tasklist`.

`python/tests/test_conventions.py` роняет набор на процессе, прочитанном как текст без кодировки,
включая форму шва для тестов `(run or subprocess.run)(...)` – ту самую, мимо которой смотрит поиск по
тексту вызова. Само чтение берётся из общего пакета
[docsguard](https://github.com/keyfire/docsguard), который сценарий `ci` ставит по тегу. Здесь
остаётся перечень каталогов.

### Запись файла

Текстовый файл, записанный из обвязки или из скрипта, называет свой конец строки: `write_text(text,
encoding="utf-8", newline="")`. Иначе текстовый режим заменяет каждый перевод строки тем, что принят
на этой системе, и генератор, запущенный на Windows, возвращает страницу с изменённой каждой
строкой. Рабочая копия с `core.autocrlf=input` убирает это при коммите, потому такое и легко
пропустить.

Пакетный файл автозапуска на Windows попал под то же правило с другой стороны. Его строки склеены
через CRLF, потому что пакетному файлу нужен именно такой конец строки, текстовый режим перевёл
каждый из них ещё раз, и на диск каждая строка ушла как `\r\r\n`.

`python/tests/test_conventions.py` роняет набор на записи, которая оставляет конец строки системе.
Проверка читает `python/src` и `scripts`, но не тесты: тест пишет во временный каталог, который
исчезает вместе с запуском, а образец с другим концом строки и есть отдельный тест.

## Стиль кода

- **Java 17** и стандартные соглашения Eclipse и OSGi. Весь доступ к модели среды держите в
  классах-гейтвеях в `...edtbridge.edt`, чтобы изменение API EDT оставалось там.
- **Английский** для всего кода, комментариев и идентификаторов.
- Один инструмент – один класс в `...edtbridge.tools`, с регистрацией в `McpServer`.
- Имена инструментов – `edt_*` в snake_case, параметры – camelCase. Имена должны быть
  самоописательными: MCP-хост показывает инструменты всех серверов одним списком, об этом сказано в
  README.

## Коммиты и pull request'ы

- Небольшие коммиты, каждый об одном, с ясным заголовком.
- Открывайте pull request в `main` и заполняйте шаблон: что изменилось, как проверено.
- Релизы выпускает сопровождающий из локально собранного jar, потому что CI плагин не компилирует.
  Влитое изменение выходит в следующем теговом релизе.
