# Участие в EDT-Bridge

Спасибо за интерес. EDT-Bridge – это плагин для 1C:EDT плюс небольшая обвязка на Python. Здесь
описаны сборка, соглашения и порядок, в котором предлагают изменения.

## Базовые правила

- **Clean-room.** EDT-Bridge – независимая реализация, написанная с нуля. Подробнее:
  [ORIGIN.md](../../ORIGIN.md). Присылайте только собственный код, построенный на открытой
  спецификации MCP и публичных API плагинов Eclipse и 1C:EDT (`org.eclipse.*`,
  `com._1c.g5.v8.dt.*`). Не вставляйте декомпилированный или иной проприетарный код из EDT или
  другого инструмента.
- **Область.** Плагин отдает по MCP *живую* модель EDT. Новому инструменту должно быть нужно то,
  чего не дает статический парсер: валидация работающей среды, настоящие типы, семантические ссылки,
  штатный рефакторинг, сборка. Остальные инструменты следует размещать отдельно от моста.
- **Лицензия.** Присылая вклад, вы соглашаетесь, что он лицензируется под
  [Apache-2.0](../../LICENSE), inbound равно outbound.

## Сборка

Нужны **JDK под вашу EDT** и локальный **пул бандлов 1C:EDT**. Плагин компилируется против
собственных бандлов EDT, а они проприетарны и берутся из вашей локальной установки, поэтому сборки
через сеть нет. Начиная с EDT 2026.2 эти бандлы содержат class-файлы Java 25. Для их чтения требуется JDK 25 или более новая версия.
Скрипт определяет уровень по пулу и сам подхватывает более новый JDK, в том числе установленный
вместе с EDT. Байткод самого jar по-прежнему нацелен на Java 17.

```powershell
# Windows – по умолчанию: -Pool %USERPROFILE%\.p2\pool\plugins, -JdkHome %JAVA_HOME% (сам сменится, если старый)
powershell -ExecutionPolicy Bypass -File scripts/build-nomaven.ps1
```

```bash
# macOS / Linux – --pool определяется автоматически из установленного компонента 1C:EDT
./scripts/build-nomaven.sh
```

Jar кладется в `build/`. Для полной сборки есть Maven и Tycho (`mvn -f pom.xml clean verify`), но
сначала отредактируйте `edt-bridge.target`. Подробнее: [README](README.ru.md#сборка-из-исходников).

## Запуск своей сборки

Скопируйте собранный jar в `dropins/` EDT и перезапустите EDT либо дайте это сделать обвязке.
Держите там ровно один jar EDT-Bridge: при двух Equinox возьмет произвольный. На Windows для
headless EDT оба шага выполняет `scripts/run-headless.ps1 -Workspace <ws> -FromBuild`: скрипт
останавливает headless-сеанс этой рабочей области, оставляет в `dropins/` только самый новый jar из
`build/` и запускает EDT. `-Jar <путь>` ставит указанный jar. Затем скрипт сравнивает
`bridgeBundleVersion` из ответа моста с версией в имени jar и при расхождении завершается с кодом 3. MCP-сервер запускается
на `http://127.0.0.1:8770/mcp`. Через страницу `http://127.0.0.1:8770/` можно запустить любой
инструмент. См. [Установку вручную](README.ru.md#установка-вручную-без-обвязки).

## Проверка изменения

Полного автономного набора тестов для Java-плагина нет. Плагин проверяется с запущенной EDT: собрать, положить в
`dropins/`, перезапустить EDT и запустить затронутые инструменты – со страницы в браузере или из
MCP-клиента. У инструментов записи сначала посмотрите план с `apply=false`, а потом уже `apply=true`.
Исполнитель GitHub не может собрать плагин: для компиляции нужны проприетарные бандлы 1C:EDT SDK. По той
же причине jar собирается локально и коммитится в `dist/`.

С обвязкой на Python иначе: она не зависит от EDT, поэтому у нее есть набор тестов pytest.

```sh
cd python
python -m pip install .[test]
python -m pytest -q
```

Сценарий `ci` запускает этот набор на каждый push и pull request – на Linux и Windows, на 3.10 и
3.12. Оба релизных сценария сначала вызывают `ci`, поэтому красный набор останавливает релиз, а не
выпускается мимо него. Проверка на Windows включена из-за ошибки кодировки, которая проявилась только на этой системе
и привела к выпуску с ошибкой.

Новое поведение обвязки ожидается вместе с тестом, а исправленная ошибка – вместе с тестом, который
ее воспроизводит. Из таких тестов набор в основном и состоит.

Часть плагина тоже покрывается тестами. Все в `...edtbridge.core` – это чистая работа со строками:
где лежат исходники объекта, относится ли проблема валидации к тому, о чем спросили. Этот пакет
намеренно свободен от типов EDT и Eclipse, поэтому компилируется обычным JDK.

```sh
scripts/test-java.sh
```

Скрипт добавляет в classpath только JUnit, поэтому зависимость `core` от SDK приводит к ошибке
сборки. Логика, которой нужна модель EDT, остается в шлюзах `...edtbridge.edt` и проверяется с
запущенной EDT, как описано выше.

### Документация

Команда `python scripts/check_docs.py` сверяет документацию с исходниками. Для каждого инструмента
и каждой переменной `EDT_BRIDGE_` требуется описание. Блоки в README должны совпадать со
страницами-источниками, а файлы изображений должны находиться в репозитории. Проверки документации
и тесты обвязки выполняются в `ci`.

Для проверки русских текстов используется словарь транслитераций из
[docsguard](https://github.com/keyfire/docsguard). Для каждого найденного слова предлагается
русская замена. Слово, которое приводится как цитата, заключается в обратные кавычки. Например,
в записи журнала можно указать замененную транслитерацию, и проверка ее пропустит.

Проверка использует тот же словарь для русских строк `python/src/edt_bridge_mcp/i18n.py`,
откуда формируется справка `--help`. Отсутствие указанного файла считается ошибкой: это позволяет
обнаружить ситуацию, когда каталог переименован и проверка не прочитала его содержимое.

`docs/changelog*.md` и `docs/onboarding*.md` создаются из исходных документов командой
`node scripts/sync-docs.mjs`. Изменения следует вносить в исходники.

### Запуск процесса

При чтении текстового вывода процесса, запущенного из обвязки или скрипта, явно указать кодировку:
`capture_output=True, text=True, encoding="utf-8"`. Для вывода, предназначенного человеку, также
указать `errors="replace"`. Без `encoding` Python использует кодовую страницу машины. Из-за ошибки
декодирования вывод может содержать символы замены или остаться пустым после исключения в потоке
чтения, хотя код завершения процесса указывает на успех. Такая ошибка мешала проверке, которая
запрещает запуск headless EDT, пока рабочая область занята EDT с интерфейсом.

Если текстовый режим не требуется, можно передавать и получать байты, а затем декодировать их
отдельно. Так выполняется опрос через `tasklist`.

При запуске дочернего процесса из обвязки указать `stdin=subprocess.DEVNULL`. Обвязка работает
MCP-сервером и использует stdin для связи с клиентом. На Windows дочерний процесс, унаследовавший
этот канал, может оставаться запущенным до истечения срока ожидания, даже если его работа занимает
миллисекунды. Команды `tasklist`, `powershell` и `cmd` закрывают свой конец канала и завершаются.
Git, интерпретатор и pip могут остаться запущенными; pip используется при самообновлении плагинов.
Дочерние процессы обвязки не получают данные через stdin. Проверка допускает вызовы, которые
передают данные через `input=` или явно задают собственный `stdin=`.

`python/tests/test_conventions.py` проверяет, что при чтении процесса в текстовом режиме указана
кодировка. Проверка охватывает и вызовы вида `(run or subprocess.run)(...)`, которые поиск по тексту
может пропустить. Анализ предоставляется пакетом [docsguard](https://github.com/keyfire/docsguard),
который сценарий `ci` устанавливает по тегу. В проекте задается перечень каталогов. Правило для stdin
проверяет только `python/src`: генератор и тесты работают из консоли и могут передавать дочернему
процессу консольный stdin.

### Запись файла

При записи текстового файла из обвязки или скрипта указать кодировку и конец строки:
`write_text(text,
encoding="utf-8", newline="")`. Без `newline=""` текстовый режим заменяет перевод строки
вариантом, принятым в системе. В результате генератор на Windows может изменить все строки страницы.
В рабочей копии с `core.autocrlf=input` это изменение удаляется при коммите, поэтому его легко
пропустить.

В пакетном файле автозапуска Windows строки уже соединены через CRLF. Если текстовый режим повторно
преобразует перевод строки, в файле получится `\r\r\n`.

`python/tests/test_conventions.py` проверяет, что конец строки задан явно. Проверка охватывает
`python/src` и `scripts`, но не тесты. Тесты записывают файлы во временный каталог, а запись с
другим концом строки проверяется отдельным тестом.

Параметр `newline=""` управляет записью. Если при чтении файла сохраняются возвраты каретки,
`scripts/sync-docs.mjs` может перенести их в оба README при вставке каталога инструментов.
В `.gitattributes` строка `* text=auto eol=lf` задает перевод строки для текстовых файлов независимо
от настроек машины. Настройка `core.autocrlf=input` действует только в той рабочей копии, где она
установлена.

### Имя теста

Если два теста в одном пространстве имен имеют одинаковое имя, Python сохраняет последнее
определение. Pytest соберет последнюю версию теста, а число тестов может увеличиться за счет
других добавленных тестов. Отчет о запуске не укажет, что прежний тест был заменен.

`python/tests/test_conventions.py` запускает `shadowed_test_problems` для каталога `python/tests` и
указывает строку повторного определения, которое требуется переименовать. Пространства имен
проверяются отдельно, поэтому методы разных классов могут иметь одинаковые имена.

## Стиль кода

- **Java 17** и стандартные соглашения Eclipse и OSGi. Весь доступ к модели среды держите в
  классах-гейтвеях в `...edtbridge.edt`, чтобы изменение API EDT оставалось там.
- **Английский** для всего кода, комментариев и идентификаторов.
- Один инструмент – один класс в `...edtbridge.tools`, с регистрацией в `McpServer`.
- Имена инструментов – `edt_*` в snake_case, параметры – camelCase. Имена должны быть
  самоописательными: MCP-хост показывает инструменты всех серверов одним списком, об этом сказано в
  README.

## Коммиты и pull request'ы

- Небольшие коммиты, каждый об одном, с ясным заголовком.
- Открывайте pull request в `main` и заполняйте шаблон: что изменилось, как проверено.
- Каждая запись журнала заканчивается ссылкой на свой pull request, в обеих редакциях. Номер
  появляется только после открытия pull request'а, поэтому ссылку добавляют отдельным коммитом:

  ```sh
  python scripts/changelog-link.py 16
  ```

  Скрипт пишет ссылку в каждую запись верхнего раздела `CHANGELOG.md` и
  `docs/ru/CHANGELOG.ru.md`, где ее еще нет, переносит ее на отдельную строку там, где запись уже
  занимает всю ширину, и пересобирает страницы-зеркала. Разделы ниже он не трогает: запись,
  сделанная до этого правила, – история, а не недоделанное изменение.
- Релизы выпускает сопровождающий из локально собранного jar, потому что CI плагин не компилирует.
  Влитое изменение выходит в следующем теговом релизе.
