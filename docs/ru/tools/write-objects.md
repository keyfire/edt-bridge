Эти инструменты создают, изменяют, переименовывают и удаляют объекты метаданных и их
реквизиты, задают свойства общих модулей, состав подсистем, права ролей и командный
интерфейс, а также заимствуют объекты в расширение.

Для записи нужен токен; без `apply=true` инструмент возвращает план. Общие правила приведены
в разделе [План и применение](/ru/tools#план-и-применение).

| Инструмент записи | Что делает |
|-------------------|------------|
| `edt_create_object` · `edt_delete_object` | Создает объект верхнего уровня – справочник, документ, перечисление, регистр сведений, роль и прочие – через фабрику EDT и инициализатор типа и регистрирует его в Configuration. Роль создается вместе с `Rights.rights`. В расширении объект создается собственным, и к его имени добавляется префикс расширения. Удаление выполняется штатным рефакторингом EDT и требует `force`. Предпросмотр показывает индексированные ссылки и возможные обращения в BSL, текстах запросов и привязках форм. Такие обращения могут остаться после удаления; ответ не обещает полный каскад. |
| `edt_add_attribute` · `edt_modify_attribute` · `edt_remove_attribute` | Добавляет или меняет реквизит, ресурс или измерение регистра (`kind`, по умолчанию `attribute`). При добавлении проверяет имя по всем трем спискам полей. Меняет тип, русский синоним и комментарий. `edt_remove_attribute` удаляет реквизиты; ресурсы и измерения удаляются через `edt_delete_object` с FQN члена. Параметр `use=ForFolder\|ForItem\|ForFolderAndItem` задает применение реквизита иерархического объекта; `multiLine` разрешает многострочный ввод. Неприменимые и неверные параметры отклоняются до записи. Изменение сохраняет UUID реквизита; `properties` содержит фактические значения. |
| `edt_rename` | Переименовывает метод, объект метаданных или член через штатный движок EDT. Предпросмотр возвращает известные затрагиваемые файлы и признаки полноты списка и счетчиков. Нужен `force`: переименование ломает все, что построено на старом имени. |
| `edt_adopt_object` | Заимствует объект базовой конфигурации в проект расширения штатным `IModelObjectAdopter`. Пока это не сделано, расширение не может перехватить у объекта ничего; этим же шагом достраивается `edt_create_extension`. |
| `edt_modify_object` · `edt_update_subsystem` | Меняет флаги выполнения и повторное использование результатов общего модуля, задает типизированные свойства корня управляемой формы (`autoTitle`, `titleRu`, `windowOpeningMode`, `scaleVariant`, `width`, `height` и другие) либо добавляет и удаляет существующие объекты из состава подсистемы. Весь запрос проверяется до записи; по умолчанию возвращается план. Удаление из состава дополнительно требует `force=true`. `extendModule=true` разрешает расширение заимствованного общего модуля. |
| `edt_modify_role_rights` | Задает права роли на один объект так же, как редактор прав EDT: значение, равное значению по умолчанию, убирает явную запись. Выгружает роль и ее `Rights.rights`; роли без собственного `Rights.rights` он создается. Неизвестное право отклоняется с перечнем прав объекта, право с ограничением доступа к данным не меняется. В расширении роль и объект должны быть собственными или заимствованными. По умолчанию dry-run, для записи нужен токен. |
| `edt_modify_command_interface` | Меняет `CommandInterface.cmi` раздела подсистемы: видимость команды общую и по ролям, ее группу в пределах панели, порядок группы, возврат к значению по умолчанию. Принимает имена, которые печатает `edt_command_interface`. Заимствованной подсистеме без своего `CommandInterface.cmi` он создается. По умолчанию dry-run, для записи нужен токен. |
| `edt_enable_configuration_editing` | Включает возможность изменения проекта на полной поддержке. Объекты поставщиков, переведенных с полной поддержки, остаются закрыты для редактирования. |
| `edt_modify_configuration_support` | Изменяет правила поддержки выбранных объектов подключенного поставщика. |

## Поддержка конфигурации

Вызовите `edt_configuration_support` с `projectName`, чтобы узнать список
подключенных поставщиков и их идентификаторы. Добавьте `fqns`, чтобы получить
правило поставщика и режим поддержки каждого объекта у этого поставщика. `edt_support_status`
проверяет, разрешает ли EDT прямое редактирование.

Например, при разработке конфигурации на основе БСП передайте в
`edt_modify_configuration_support` корень и переопределяемый общий модуль.
Подставьте идентификатор поставщика и имя модуля из своего проекта.

```json
{
  "projectName": "ДемоКонфигурация",
  "supplierId": "9140cba5-822d-4bed-89ba-f631781a0773",
  "fqns": ["Configuration", "CommonModule.ПечатьПереопределяемый"],
  "mode": "CHANGES_ALLOWED"
}
```

Предпросмотр показывает текущее и новое правило для каждого изменяемого объекта
и предупреждение поставщика, если оно есть. Для применения добавьте в запрос
`"apply": true`. Поле `applied` подтверждает изменение модели. Поле
`exportScheduled` означает, что EDT принял запрос на запись настроек на диск.
Режим `CANCELLED` снимает выбранные объекты с поддержки, если поставщик это допускает.

Для проекта на полной поддержке сначала вызовите `edt_enable_configuration_editing`
с `projectName`. Добавьте `"apply": true`, чтобы выполнить переход. EDT оставляет
объекты таких поставщиков в режиме `CHANGES_NOT_ALLOWED`. После перехода откройте
для редактирования нужные объекты, как в примере выше.

Для возврата режима "Не редактируется" передайте `mode` со значением
`CHANGES_NOT_ALLOWED`. Мост сравнивает каждый выбранный объект верхнего уровня
с релизом поставщика, указанным в настройках поддержки. Релиз должен быть
доступен в репозитории библиотек EDT. Сравнение проверяет метаданные и содержимое
модулей. Правило поставки или поддержки может присутствовать только с одной
стороны, если содержимое объекта совпадает. Если EDT сообщает об изменении
объекта или релиз поставщика недоступен, весь запрос отклоняется.
При применении мост повторяет сравнение и записывает только правила поддержки.

Перед сравнением сохраните изменения в редакторах объекта. Если EDT требует
менять его правило вместе с правилами дочерних объектов, запрос отклоняется.

## Удаление объекта

`edt_delete_object` разделяет ссылки из индекса EDT и лексические кандидаты в `referenceAudit`.
`scanComplete` относится к указанной области файлов; `complete=false` явно ограничивает семантическое покрытие.
Перед удалением с `force` проверьте `countIsLowerBound`, ошибки и образцы. После применения
`deletionConfirmed` подтверждает отсутствие цели в живой BM-модели. `remainingPossibleReferences`
и `retainedFormControls` показывают оставшиеся обращения и элементы с очищенной привязкой;
ответ указывает границы ожидания экспорта и проверки после операции.

## Поля регистров

`edt_add_attribute` и `edt_modify_attribute` принимают `kind`: `attribute` (по умолчанию),
`resource` или `dimension`. Для ресурса или измерения владелец должен поддерживать
соответствующий список полей. Поддерживаются регистры сведений, накопления, бухгалтерии
и расчета. Вызовы без `kind` по-прежнему адресуют реквизит.

При добавлении имя проверяется без учета регистра среди `attributes`, `resources`
и `dimensions` владельца, повторно – внутри транзакции записи. При совпадении ответ
содержит `nameAvailable=false` и точные `conflictingFqns`. Предпросмотр ничего не записывает.

Для ресурсов регистров накопления, бухгалтерии и расчета укажите один явный тип
`Число`, например `Число(15,2)`. Нечисловой, составной, ссылочный или определяемый тип
для такого ресурса отклоняется до записи. У ресурсов регистра сведений сохраняется
общая грамматика типов. Явный `kind` выбирает этот список, даже если в старой конфигурации
есть одноименное поле другого вида; дубли внутри выбранного списка дают отказ.

Пример предпросмотра добавления ресурса:

```json
{
  "projectName": "Demo",
  "ownerFqn": "InformationRegister.Versions",
  "kind": "resource",
  "name": "Version",
  "type": "Строка(20)"
}
```

Для изменения поля вызовите `edt_modify_attribute` с теми же владельцем, именем и видом
и хотя бы одним из `newType`, `newSynonymRu` или `newComment`. Пустой синоним или комментарий
очищает значение; отсутствие параметра сохраняет его. Смена типа возвращает предупреждение
о совместимости данных и кода. Обе операции требуют `apply=true` для записи. Ответ различает
фиксацию в модели и прием запроса экспорта; прием запроса не подтверждает завершение сериализации.

`edt_remove_attribute` по-прежнему удаляет только реквизиты. Если изменение или удаление
адресует ресурс или измерение как реквизит, ответ указывает фактический FQN члена
и подсказывает `kind`, `edt_delete_object` и `edt_rename`. Для удаления или переименования
таких полей используйте последние два инструмента с `targetFqn`, например
`InformationRegister.Versions.Resource.Version`.

## Переименование

`edt_rename` принимает `method="CommonModule.Api.Run"` либо `methodName="Run"` с FQN владельца
или `modulePath`. Используется штатный рефакторинг методов EDT. До `apply=true, force=true`
предпросмотр показывает `affectedFiles` с числом изменений и текстовых замен. Перед применением
нужно сохранить затрагиваемые редакторы.
`nativeTextEditCount` считает текстовые правки, доступные через EDT. Для операций модели
возможны `editCount=null` и `editCountComplete=false`; число операций остается в `changeCount`.
Режим метаданных также возвращает `targetPath`. Часть операций рефакторинга метаданных
не раскрывает привязку к файлу: такой предпросмотр помечен `coverageComplete=false`,
`unmappedItemCount` и `unmappedItems`. Известные файлы тогда составляют только часть списка;
перед применением нужно просмотреть штатные `items`.

## Роли

`edt_create_object` с `objectType="Роль"` создает роль вместе с ее `Rights.rights`. Файл прав –
отдельный объект модели, который мастер новой роли EDT добавляет рядом с ролью. Мост создает его
тем же шагом и заполняет так же, как конфигуратор заполняет новую роль:

- В конфигурации роль устанавливает на конфигурацию режимы основного окна и право клиента системы
  аналитики. В конфигурации со старым режимом совместимости части этих прав нет, и они
  пропускаются.
- В расширении роль создается собственной и не устанавливает прав: расширение не может
  устанавливать права на конфигурацию.

В обоих случаях права для новых объектов не устанавливаются, а для реквизитов и табличных частей
устанавливаются по умолчанию. Предпросмотр перечисляет начальные права в `rights`. После
`apply=true` поле `rightsFqn` называет файл прав.

В расширении к имени нового объекта добавляется префикс расширения, если имя еще не начинается
с него; регистр при сравнении не учитывается. Это относится к любому типу объекта, а не только к
ролям. `name` – имя, которое получит объект, `namePrefix` – префикс, а `requestedName` – имя в
том виде, в каком его передали, если к нему добавлен префикс.

Права на объекты задает `edt_modify_role_rights`, по одному объекту за вызов, после создания
роли. Собственная роль расширения устанавливает права на собственные и заимствованные объекты
расширения, поэтому объект базовой конфигурации сначала заимствуйте через `edt_adopt_object`.
`edt_role_rights` и `edt_modify_role_rights` принимают и роль без собственного `Rights.rights`,
например основную роль, которую создает мастер нового расширения конфигурации. Первая запись прав
создает этот файл.

Например, предпросмотр роли в расширении с префиксом `Расш_`:

```json
{
  "projectName": "DemoExt",
  "objectType": "Роль",
  "name": "Менеджер"
}
```

План называет `Role.Расш_Менеджер`. После `apply=true` заимствуйте `Catalog.Товары` и дайте роли
права на его чтение:

```json
{
  "projectName": "DemoExt",
  "role": "Role.Расш_Менеджер",
  "object": "Catalog.Товары",
  "rights": {"Read": true, "View": true}
}
```

## Общие модули и подсистемы

Для нового общего модуля `edt_create_object` принимает объект `properties`. Такой же объект
принимает `edt_modify_object` для существующего модуля: `global`, `server`, `externalConnection`,
`clientManagedApplication`, `clientOrdinaryApplication`, `serverCall` и `privileged` имеют булев
тип; `returnValuesReuse` принимает `DontUse`, `DuringRequest` или `DuringSession`. Флаги выполнения
заимствованного модуля определяются базовой конфигурацией. `extendModule=true` в
`edt_adopt_object` или `edt_modify_object` разрешает расширение заимствованного общего модуля
без замены его тела. `edt_update_subsystem` принимает `fqn` и массивы FQN объектов в `add` и
`remove`. Создание и заимствование сохраняют уже алфавитный список Configuration без учета
регистра. В списке с произвольным порядком новый объект добавляется в конец.

`edt_modify_object` также принимает FQN управляемой формы и объект `properties`: `autoTitle`,
`showTitle`, `showCloseButton` и `allowFormCustomize` (булевы), `titleRu` (строка, пустая очищает
заголовок), `windowOpeningMode` (`Independent`, `LockOwnerWindow`, `LockWholeInterface`),
`scaleVariant` (`Auto`, `Compact`, `Normal`, `NormalIfPossible`), `width` и `height`
(неотрицательные целые). Список свойств и текущие значения возвращает `edt_property_reference` по
FQN формы. Параметр `extendModule` относится только к заимствованным общим модулям.
