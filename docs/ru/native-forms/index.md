`edt-bridge-mcp test-form` открывает управляемую форму в настоящем клиенте тестирования
1С:Предприятия, выполняет действия в интерфейсе и записывает наблюдаемый результат.
JSON-сценарий проверяет представления полей, ячейки табличного документа и сообщения
пользователю. Дополнительная сессия проверяет состояние после повторного открытия той же цели.

Команда работает независимо от EDT. Она создает временную базу менеджера и запускает
отдельные процессы TestManager и TestClient. Целевое приложение работает с явно указанной
файловой базой; копию этой базы команда не создает. Команды интерфейса могут менять ее данные.

## Подготовка окружения

1. Использовать изолированное Linux-окружение с полной установкой платформы, содержащей
   `1cv8` и `ibcmd`, лицензией платформы, `Xvfb` и `libX11`.
2. Подготовить одноразовую файловую базу с `1Cv8.1CD`, нужной конфигурацией и тестовыми
   данными. Для проверки расширения заранее установить `.cfe`. Команда `test-form`
   не устанавливает расширения и не обновляет конфигурацию целевой базы.
3. Подготовить тестового пользователя, под которым клиент запускается без диалога входа.
   Параметр `--user` задает имя; пароль и ответы на диалоги входа CLI не принимает.
4. Разрешить запуск выбранных внешних файлов в тестовом окружении. CLI не отключает
   защиту платформы от опасных действий и не подтверждает ее предупреждение, но проверяет
   ее настройку до запуска клиента (см. ниже).

Для автоматического запуска в одноразовом окружении владелец стенда может настроить
защиту до начала проверки. В Linux-установке платформы, выбранной через `--platform-bin`,
используется файл `<platform-bin>/conf/conf.cfg`. Например, ограничить настройку базами
в каталоге `/srv/test-bases/`:

```ini
DisableUnsafeActionProtection=.*/srv/test-bases/.*
```

Это POSIX Basic Regular Expression для строки соединения с информационной базой,
а не для пути внешнего файла. Настройка отключает защиту для всех пользователей
подходящих баз. Применять ее только в одноразовом тестовом окружении; при замене
каталога в примере сохранить окружающие `.*`. Файл `conf.cfg` на Windows-хосте не
настраивает Linux-платформу внутри контейнера. Если предупреждение осталось, проверка
оставляет его на экране и сохраняет снимок, когда экран клиента доступен.

До запуска клиента `test-form` читает `<platform-bin>/conf/conf.cfg`, каталог, названный в его
`ConfLocation`, и `conf/conf.cfg` корня установки (`/opt/1cv8/conf/conf.cfg` для
`/opt/1cv8/x86_64/<версия>`); настройка берется из первого файла, где она есть. Собственный файл
пользователя `~/.1cv8/1C/1cv8/conf/conf.cfg` не учитывается: проверка запускает клиент со своим
домашним каталогом.

Если проверяется `.epf` или `.erf` без `--user` и ни один из этих файлов не задает
`DisableUnsafeActionProtection`, команда останавливается со статусом `client_environment` до
запуска процессов платформы. Сообщение называет настройку, файл и шаблон для этой базы. Если
шаблоны заданы, но ни один не подходит, проверка выполняется и записывает `warning`. Шаблоны
сопоставляются по правилам платформы так, как их понимает проверка: POSIX Basic Regular
Expression со всей строкой соединения `File="<тестовая база>";`. Путь без окружающих `.*` не
подходит: с таким шаблоном платформа 8.5.1.1529 оставила предупреждение безопасности. С `--user`
защиту может отключать флажок *Защита от опасных действий* самого пользователя, поэтому проверка
выполняется и записывает примечание. `edt_test_form` работает с копией тестовой базы во
временном каталоге `edt-bridge-form-run-*` внутри `TMPDIR`; шаблон `.*/edt-bridge-form-run-.*`
подходит к любой копии.

Что сказано в файлах, результат показывает в `clientEnvironment`: прочитанные файлы,
строку соединения, шаблоны и подошедший шаблон, значение `SystemLanguage`. Параметр
`SystemLanguage` задает язык интерфейса платформы. На этом языке подписи штатных форм
платформы, например кнопки стандартной формы отчета, поэтому его стоит задать, например
`SystemLanguage=RU`, если сценарий нажимает такую кнопку по подписи.

## Выбор цели

Для каждого запуска обязательны `--platform-bin`, `--test-infobase`, `--scope`,
`--form` и `--output-dir`; `--form-title` необязателен. Выбрать ровно одну цель:

| Параметр | Цель |
| --- | --- |
| `--epf FILE` | Существующая внешняя обработка и ее основная управляемая форма, например `ExternalDataProcessor.Check.Form.Main`. |
| `--erf FILE` | Существующий внешний отчет с назначенной основной формой или основной схемой компоновки данных. |
| `--navigation-link LINK` | Существующий документ или элемент справочника в выбранной базе. Требует `--scenario`. |

Для EPF или ERF с назначенной основной формой укажите ее полное имя, например
`ExternalReport.PlannedShipments.Form.Main`. Для ERF с основной схемой компоновки
данных и без назначенной формы используйте `ExternalReport.PlannedShipments.Form`.
Платформа создаст штатную форму.

Для объекта конфигурации укажите полное имя формы, например
`Document.CustomerOrder.Form.Main` или `Catalog.Items.Form.Main`. Принимаются
русские имена, например `ВнешнийОтчет.PlannedShipments.Форма`.

Без `--form-title` проверка ждет форму по полному имени и берет ее, если открыта одна форма
с таким именем. В `--form-title` передается заголовок окна в клиенте. Окно формы объекта
дописывает к заголовку формы представление объекта: форма с заголовком "Контроль отгрузки"
открывается окном "Контроль отгрузки: КонтрольОтгрузки", и точный заголовок формы не совпадет;
передавать шаблон вида `'Контроль отгрузки*'`. Платформа считает `*` любой
последовательностью символов, а `?` – одним символом, поэтому заголовок с датой или
номером можно задать шаблоном, например `'Заказ покупателя 7 от *'`. Дата в
заголовке документа следует региональным установкам сеанса, и точный заголовок,
снятый при другой локали, не совпадет. Форма по-прежнему выбирается по полному имени:
окна, подходящие под шаблон, но с другим именем формы, пропускаются, а два подходящих
окна с одним именем формы дают `ambiguous_form`. Заголовок только из знаков
подстановки отклоняется. `--button` остается точным заголовком кнопки.

При `form_not_found` JSON перечисляет открытые формы в `observedForms`, а их
заголовки – в `observedTitles`. Найденная форма записывается в `observedForm` и
`observedTitle`.

Ссылка на объект конфигурации имеет следующий вид:

```text
e1cib/data/Document.CustomerOrder?ref=0123456789abcdef0123456789abcdef
```

Использовать ссылку реального объекта из одноразовой базы. Идентификатор содержит
32 шестнадцатеричных символа; тип и имя объекта метаданных должны совпадать с `--form`.
Принимаются только внутренние ссылки `e1cib/data/` на документы и элементы справочников.
Внешние ссылки, ссылки на команды и дополнительные параметры отклоняются.

Параметр `--scope` записывает заявленную вызывающим область проверки: `empty`, `fixture`
или `application`. Команда не исследует базу, чтобы подтвердить эту классификацию.
Параметр `--output-dir` должен указывать новый каталог вне базы; недостающие родительские
каталоги создаются. Предел `--timeout` составляет 1–900 секунд, по умолчанию 120; он включает
подготовку и все фазы сценария. Для завершения процессов предусмотрен отдельный короткий
срок. Все параметры приведены в [справочнике CLI](/ru/cli#edt-bridge-mcp-test-form).

ERF открывается фиксированной временной обработкой в том же клиенте через
`ExternalReports.Connect` и `OpenForm` с `SafeMode=True`. Тестовый пользователь должен иметь
разрешение на запуск этой обработки. Такой программный маршрут проверяет выполнение
отчета и доступ к данным; право на интерактивную команду открытия файла требует
отдельной проверки.

## Существующая проверка одной кнопки

Профиль EPF по-прежнему принимает `--epf`, `--button` и `--expect-message`. После нажатия
число вхождений ожидаемого сообщения должно увеличиться. Без `--expect-message`
результат – `command_observed`, `ok=false`, код возврата 2. Для точного числа сообщений,
проверки их отсутствия или проверки данных использовать `--scenario`. Параметры
`--button` и `--scenario` взаимоисключающие; `--expect-message` со сценарием не применяется.
