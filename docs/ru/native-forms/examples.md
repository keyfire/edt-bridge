## Проверка внешнего отчета

Пример предполагает подготовленный отчет с внутренними именами полей `StartDate`,
`EndDate`, `Result` и указанными ниже русскими заголовками. Заменить имена, заголовки
и ожидаемые строки на данные своего отчета и контрольного набора. Сохранить сценарий
в `/srv/scenarios/shipments.json`:

```json
{
  "version": 1,
  "steps": [
    {"action": "input", "field": "StartDate", "text": "01.11.2026"},
    {"action": "input", "field": "EndDate", "text": "30.11.2026"},
    {"action": "click", "button": "Сформировать"},
    {"action": "assert_table_size", "field": "Result", "rows": 2, "columns": 7},
    {"action": "assert_cell", "field": "Result", "cell": "R2C6", "equals": "100,00"},
    {
      "action": "assert_table",
      "field": "Result",
      "equals": [
        ["Дата отгрузки", "Номер", "Дата заказа", "Организация", "Контрагент", "Сумма", "Валюта"],
        ["05.11.2026", "000001", "04.11.2026", "Тестовая организация", "Тестовый покупатель", "100,00", "RUB"]
      ]
    }
  ]
}
```

```bash
edt-bridge-mcp test-form \
  --platform-bin /opt/1cv8/x86_64/8.5.1.1529 \
  --test-infobase /srv/test-bases/orders --scope fixture \
  --erf /srv/artifacts/PlannedShipments.erf \
  --form ExternalReport.PlannedShipments.Form.Main \
  --form-title 'Плановые отгрузки' --user Tester \
  --scenario /srv/scenarios/shipments.json \
  --output-dir /srv/results/shipments-01 --timeout 300
```

Действие `assert_table` сравнивает фактический текст ячеек и порядок строк. Нажатие
"Сформировать" или сообщение о завершении не заменяют проверку содержимого отчета.

## Проверка установленного расширения и сохраненных значений

Подготовить документ, установить расширение и записать исходные значения контрольного
набора. В примере ожидается предупреждение, если плановая дата отгрузки раньше даты заказа,
затем сохраненные даты проверяются в другой сессии. Сохранить сценарий
в `/srv/scenarios/order.json`:

```json
{
  "version": 1,
  "steps": [
    {"action": "assert_field", "field": "OrderDate", "equals": "06.11.2026 12:00:00"},
    {"action": "input", "field": "PlannedShipmentDate", "text": "05.11.2026"},
    {"action": "click", "button": "Записать"},
    {"action": "assert_messages", "text": "Плановая дата отгрузки раньше даты заказа.", "count": 1},
    {"action": "assert_field", "field": "PlannedShipmentDate", "equals": "05.11.2026"}
  ],
  "reopen": [
    {"action": "assert_field", "field": "OrderDate", "equals": "06.11.2026 12:00:00"},
    {"action": "assert_field", "field": "PlannedShipmentDate", "equals": "05.11.2026"}
  ]
}
```

```bash
edt-bridge-mcp test-form \
  --platform-bin /opt/1cv8/x86_64/8.5.1.1529 \
  --test-infobase /srv/test-bases/orders --scope application \
  --navigation-link 'e1cib/data/Document.CustomerOrder?ref=0123456789abcdef0123456789abcdef' \
  --form Document.CustomerOrder.Form.Main \
  --form-title 'Заказ покупателя 000001' --user Tester \
  --scenario /srv/scenarios/order.json \
  --output-dir /srv/results/order-01 --timeout 300
```

После окончания первой фазы `reopen` запускает новые сессии TestClient и TestManager
для той же базы, пользователя и цели. Допустимы только `assert_field`, `assert_cell`,
`assert_table` и `assert_table_size`. Отредактированная форма не используется повторно,
запись вместо сценария не выполняется. При открытии формы по-прежнему работают ее
прикладные обработчики.

Для проверки штатного отказа в записи подготовить данные, которые вызывают проверку
самой конфигурации. Попытаться изменить данные, проверить штатное сообщение отказа,
а в `reopen` ожидать исходные сохраненные значения. Включить реквизит, который фактически
менялся в первой фазе, чтобы отсутствие записи не выглядело успешным обновлением.
Проверка поля в первой фазе читает открытую форму и не доказывает сохранение данных.
Для случаев без дополнительного предупреждения расширения использовать отдельный
запуск с `assert_messages` и `count: 0`.

Если при отказе открывается стандартный диалог ошибки платформы, добавить к шагу
`click` поле `expect_error_dialog` с точным текстом сообщения. Например:

```json
{"action": "click", "button": "Записать", "expect_error_dialog": "Не удалось записать заказ."}
```

Менеджер сверяет текст `ErrorInfo` формы `ErrorWindow` перед нажатием ее кнопки `OK`.
При другом тексте проверка завершается неуспешно; диалог остается открытым для снимка.
Фактический текст и результат закрытия записываются в отчет. Параметр не обрабатывает
другие диалоги и не заменяет проверки сообщений и сохраненных данных.

Если команда отвечает окном предупреждения (`ПоказатьПредупреждение`), а не сообщением,
добавить к шагу `click` поле `expect_warning` с точным текстом окна:

```json
{"action": "click", "button_name": "ФормаЗаписать", "expect_warning": "Проверьте дату отгрузки."}
```

Менеджер находит окно поверх формы – системную форму `MessageBox`, которая получает номер
(`MessageBox85`), если окно открыла форма объекта. Он сверяет текст надписи `Message`, нажимает
`OK` и переходит к следующему шагу, поэтому предупреждение в `ПередЗаписью` не мешает проверить
записанные значения. При другом тексте проверка завершается `assertion_failed` с фактическим
текстом, а нажатие без окна предупреждения завершает шаг ошибкой. Шаг ждет одно окно:
`expect_error_dialog` и `expect_warning` взаимоисключающие.
