`edt-bridge-mcp test-form` открывает управляемую форму в настоящем клиенте тестирования
1С:Предприятия, выполняет действия в интерфейсе и записывает наблюдаемый результат.
JSON-сценарий проверяет представления полей, ячейки табличного документа и сообщения
пользователю. Дополнительная сессия проверяет состояние после повторного открытия той же цели.

Команда работает независимо от EDT. Она создает временную базу менеджера и запускает
отдельные процессы TestManager и TestClient. Целевое приложение работает с явно указанной
файловой базой; копию этой базы команда не создает. Команды интерфейса могут менять ее данные.

## Подготовка окружения

1. Использовать изолированное Linux-окружение с полной установкой платформы, содержащей
   `1cv8` и `ibcmd`, лицензией платформы, `Xvfb` и `libX11`.
2. Подготовить одноразовую файловую базу с `1Cv8.1CD`, нужной конфигурацией и тестовыми
   данными. Для проверки расширения заранее установить `.cfe`. Команда `test-form`
   не устанавливает расширения и не обновляет конфигурацию целевой базы.
3. Подготовить тестового пользователя, под которым клиент запускается без диалога входа.
   Параметр `--user` задает имя; пароль и ответы на диалоги входа CLI не принимает.
4. Разрешить запуск выбранных внешних файлов в тестовом окружении. CLI не отключает
   защиту платформы от опасных действий и не подтверждает ее предупреждение, но проверяет
   ее настройку до запуска клиента (см. ниже).

Для автоматического запуска в одноразовом окружении владелец стенда может настроить
защиту до начала проверки. В Linux-установке платформы, выбранной через `--platform-bin`,
используется файл `<platform-bin>/conf/conf.cfg`. Например, ограничить настройку базами
в каталоге `/srv/test-bases/`:

```ini
DisableUnsafeActionProtection=.*/srv/test-bases/.*
```

Это POSIX Basic Regular Expression для строки соединения с информационной базой,
а не для пути внешнего файла. Настройка отключает защиту для всех пользователей
подходящих баз. Применять ее только в одноразовом тестовом окружении; при замене
каталога в примере сохранить окружающие `.*`. Файл `conf.cfg` на Windows-хосте не
настраивает Linux-платформу внутри контейнера. Если предупреждение осталось, проверка
оставляет его на экране и сохраняет снимок, когда экран клиента доступен.

До запуска клиента `test-form` читает `<platform-bin>/conf/conf.cfg`, каталог, названный в его
`ConfLocation`, и `conf/conf.cfg` корня установки (`/opt/1cv8/conf/conf.cfg` для
`/opt/1cv8/x86_64/<версия>`); настройка берется из первого файла, где она есть. Собственный файл
пользователя `~/.1cv8/1C/1cv8/conf/conf.cfg` не учитывается: проверка запускает клиент со своим
домашним каталогом.

Если проверяется `.epf` или `.erf` без `--user` и ни один из этих файлов не задает
`DisableUnsafeActionProtection`, команда останавливается со статусом `client_environment` до
запуска процессов платформы. Сообщение называет настройку, файл и шаблон для этой базы. Если
шаблоны заданы, но ни один не подходит, проверка выполняется и записывает `warning`. Шаблоны
сопоставляются по правилам платформы так, как их понимает проверка: POSIX Basic Regular
Expression со всей строкой соединения `File="<тестовая база>";`. Путь без окружающих `.*` не
подходит: с таким шаблоном платформа 8.5.1.1529 оставила предупреждение безопасности. С `--user`
защиту может отключать флажок *Защита от опасных действий* самого пользователя, поэтому проверка
выполняется и записывает примечание. `edt_test_form` работает с копией тестовой базы во
временном каталоге `edt-bridge-form-run-*` внутри `TMPDIR`; шаблон `.*/edt-bridge-form-run-.*`
подходит к любой копии.

Что сказано в файлах, результат показывает в `clientEnvironment`: прочитанные файлы,
строку соединения, шаблоны и подошедший шаблон, значение `SystemLanguage`. Параметр
`SystemLanguage` задает язык интерфейса платформы. На этом языке подписи штатных форм
платформы, например кнопки стандартной формы отчета, поэтому его стоит задать, например
`SystemLanguage=RU`, если сценарий нажимает такую кнопку по подписи.

## Выбор цели

Для каждого запуска обязательны `--platform-bin`, `--test-infobase`, `--scope`,
`--form` и `--output-dir`; `--form-title` необязателен. Выбрать ровно одну цель:

| Параметр | Цель |
| --- | --- |
| `--epf FILE` | Существующая внешняя обработка и ее основная управляемая форма, например `ExternalDataProcessor.Check.Form.Main`. |
| `--erf FILE` | Существующий внешний отчет с назначенной основной формой или основной схемой компоновки данных. |
| `--navigation-link LINK` | Существующий документ или элемент справочника в выбранной базе. Требует `--scenario`. |

Для EPF или ERF с назначенной основной формой укажите ее полное имя, например
`ExternalReport.PlannedShipments.Form.Main`. Для ERF с основной схемой компоновки
данных и без назначенной формы используйте `ExternalReport.PlannedShipments.Form`.
Платформа создаст штатную форму.

Для объекта конфигурации укажите полное имя формы, например
`Document.CustomerOrder.Form.Main` или `Catalog.Items.Form.Main`. Принимаются
русские имена, например `ВнешнийОтчет.PlannedShipments.Форма`.

Без `--form-title` проверка ждет форму по полному имени и берет ее, если открыта одна форма
с таким именем. В `--form-title` передается заголовок окна в клиенте. Окно формы объекта
дописывает к заголовку формы представление объекта: форма с заголовком "Контроль отгрузки"
открывается окном "Контроль отгрузки: КонтрольОтгрузки", и точный заголовок формы не совпадет;
передавать шаблон вида `'Контроль отгрузки*'`. Платформа считает `*` любой
последовательностью символов, а `?` – одним символом, поэтому заголовок с датой или
номером можно задать шаблоном, например `'Заказ покупателя 7 от *'`. Дата в
заголовке документа следует региональным установкам сеанса, и точный заголовок,
снятый при другой локали, не совпадет. Форма по-прежнему выбирается по полному имени:
окна, подходящие под шаблон, но с другим именем формы, пропускаются, а два подходящих
окна с одним именем формы дают `ambiguous_form`. Заголовок только из знаков
подстановки отклоняется. `--button` остается точным заголовком кнопки.

При `form_not_found` JSON перечисляет открытые формы в `observedForms`, а их
заголовки – в `observedTitles`. Найденная форма записывается в `observedForm` и
`observedTitle`.

Ссылка на объект конфигурации имеет следующий вид:

```text
e1cib/data/Document.CustomerOrder?ref=0123456789abcdef0123456789abcdef
```

Использовать ссылку реального объекта из одноразовой базы. Идентификатор содержит
32 шестнадцатеричных символа; тип и имя объекта метаданных должны совпадать с `--form`.
Принимаются только внутренние ссылки `e1cib/data/` на документы и элементы справочников.
Внешние ссылки, ссылки на команды и дополнительные параметры отклоняются.

Параметр `--scope` записывает заявленную вызывающим область проверки: `empty`, `fixture`
или `application`. Команда не исследует базу, чтобы подтвердить эту классификацию.
Параметр `--output-dir` должен указывать новый каталог вне базы; недостающие родительские
каталоги создаются. Предел `--timeout` составляет 1–900 секунд, по умолчанию 120; он включает
подготовку и все фазы сценария. Для завершения процессов предусмотрен отдельный короткий
срок. Все параметры приведены в [справочнике CLI](cli.ru.md#edt-bridge-mcp-test-form).

ERF открывается фиксированной временной обработкой в том же клиенте через
`ExternalReports.Connect` и `OpenForm` с `SafeMode=True`. Тестовый пользователь должен иметь
разрешение на запуск этой обработки. Такой программный маршрут проверяет выполнение
отчета и доступ к данным; право на интерактивную команду открытия файла требует
отдельной проверки.

## Формат сценария

Передать UTF-8 JSON-файл через `--scenario`. Верхний уровень содержит `version: 1`,
массив `steps` и необязательный массив `reopen`. В каждой фазе от 1 до 128 шагов;
после последнего действия в интерфейсе должна следовать проверка или чтение. Неизвестные поля
и повторяющиеся JSON-ключи отклоняются; отказ называет шаг, его лишние и недостающие ключи и
ключи, которые принимает его действие, например `Invalid 'input' step 1 in steps: unexpected value;
missing text; input takes action, field, text.` Схема `edt_test_form` описывает каждый вид шага. Предел размера файла – 1 МиБ.

Каждый шаг содержит обязательные поля из таблицы ниже. Поле `field` задает
внутреннее имя видимого элемента формы. В шаге `click` укажите одно из двух полей.
`button` задает точный видимый заголовок, а `button_name` – внутреннее имя элемента
кнопки. Если заголовок встречается у нескольких кнопок, используйте `button_name`.
Селектор должен находить ровно один элемент. Маски отклоняются.
Шаг `click` также может содержать `expect_error_dialog` или `expect_warning`.

| `action` | Остальные обязательные поля | Операция |
| --- | --- | --- |
| `input` | `field`, `text` | Заменяет текст поля ввода и переводит фокус на следующий элемент формы. Пустой текст вызывает штатное действие `Clear()`. |
| `click` | `button` или `button_name` | Нажимает доступную кнопку. Читает панель сообщений до и после нажатия, если его результат проверяет `assert_messages`. |
| `assert_field` | `field`, `equals` | Читает `GetDataPresentation()` и сравнивает возвращенную строку. |
| `assert_cell` | `field`, `cell`, `equals` | Читает одну ячейку табличного документа, например `"cell": "R3C6"`, и сравнивает ее текст. |
| `assert_table` | `field`, `equals` | Читает прямоугольник от `R1C1` до последней заполненной строки и колонки или все строки таблицы формы; сравнивает полный массив строк. Для таблицы формы результат называет и колонки. |
| `assert_table_size` | `field`, `rows`, `columns` | Сравнивает номера последней заполненной строки и колонки табличного документа. |
| `assert_messages` | `text`, `count` | Проверяет точное число вхождений сообщения после предшествующего нажатия при нулевом числе до него. |
| `read_form` | – | Возвращает значения всей формы: каждое видимое поле с `name`, `title` и `presentation`, каждую видимую таблицу формы с `columns` и `rows`, каждое поле табличного документа строками. Ничего не сравнивает. |
| `read_table` | `field` | Возвращает одну таблицу формы вместе с колонками или одно поле табличного документа строками. Ничего не сравнивает. |

Значения `text` и одиночного `equals` – строки, в том числе для дат и чисел. Их длина
ограничена 4096 символами. Сравнение учитывает регистр, пробелы и форматирование.
Использовать фактический формат ввода и представления тестового клиента. API не возвращает
исходное типизированное значение реквизита. Если возвращенное представление не содержит
времени, такое сравнение не позволяет доказать его сохранность.

Проверки `assert_cell` и `assert_table_size` работают только с полем табличного документа.
`assert_table` и `read_table` принимают поле табличного документа или таблицу формы, в том
числе динамический список, по имени элемента. Таблица формы читается тестовым клиентом
построчно с первой строки: текст ячейки каждой видимой колонки. Действие `assert_table` принимает прямоугольный массив строк:
до 200 строк и 50 колонок. Если фактический документ больше, проверка завершается ошибкой.
В результат входят шапки, итоги и пустые ячейки внутри прямоугольника. Действие
`assert_table_size` измеряет границы заполненной области, а не количество записей данных.
Значение `rows` – от 0 до 999999, `columns` – от 0 до 99999. В адресе `cell` номера
строки и колонки положительные, в тех же пределах. Пустой табличный документ можно
проверить через `"equals": []`.

Перед `assert_messages` должен быть `click` без промежуточного `input`. Используются
снимки панели до и после этого нажатия, даже если между ним и проверкой есть другие
проверки. Поле `count` содержит целое число от 0 до 10000: сколько сообщений с точно
таким текстом добавило нажатие; ноль проверяет, что не добавило ни одного. Сообщения,
которые уже были в панели, не считаются, поэтому второе нажатие той же команды снова
проверяется с `count` 1. Команда дописывает сообщения после прежних, а очистка панели
убирает их все: если прежние сообщения больше не стоят в начале панели, она была
очищена, и новым считается все, что в ней есть. Поле `panel` в проверке говорит, что
произошло: `appended`, `cleared` или `unchanged`. Если панель не изменилась, а текст в
ней уже был, результат – `message_baseline_not_empty`: команда либо ничего не написала,
либо очистила панель и написала те же сообщения заново, и различить это нельзя. Если
команда очищает панель перед записью, дайте повторному сообщению отличающийся текст или
проверяйте его отдельным запуском. Проверяется панель сообщений,
а не модальные предупреждения или кратковременные оповещения. Прочитать сообщения до
закрытия формы: команда "Записать и закрыть" может убрать панель.

Шаги `read_form` и `read_table` кладут прочитанное в `reads` результата с номером шага, а
оценку оставляют вызывающему. Тестовый клиент видит только элементы формы: реквизит без
элемента на форме не читается, скрытый элемент пропускается. Чтобы проверить такое значение,
его нужно вывести на форму, например полем только для просмотра. Поле, представление которого
прочитать не удалось, содержит `error` вместо `presentation`. Чтение отбрасывает то, что не
укладывается в пределы (500 элементов формы, 200 строк и 50 колонок таблицы), и ставит `truncated`
у формы, таблицы или шага. `assert_table` при превышении пределов отказывает: он сравнивает только
полные таблицы. Таблица формы читается с первой строки вниз. Неудачный переход к следующей строке
считается концом таблицы, только если курсор стоит на последней строке; иначе шаг завершается
ошибкой, и сбой чтения не выглядит как короткая таблица.

Менеджер записывает наблюдения; Python сравнивает ожидания после завершения всей фазы.
Несовпадение промежуточной проверки не останавливает последующие действия в той же фазе.
Ошибка выполнения действия останавливает фазу. После неуспешных проверок фаза `reopen`
не запускается. Сценарий не содержит произвольного BSL или собственного условия успеха.

## Проверка внешнего отчета

Пример предполагает подготовленный отчет с внутренними именами полей `StartDate`,
`EndDate`, `Result` и указанными ниже русскими заголовками. Заменить имена, заголовки
и ожидаемые строки на данные своего отчета и контрольного набора. Сохранить сценарий
в `/srv/scenarios/shipments.json`:

```json
{
  "version": 1,
  "steps": [
    {"action": "input", "field": "StartDate", "text": "01.11.2026"},
    {"action": "input", "field": "EndDate", "text": "30.11.2026"},
    {"action": "click", "button": "Сформировать"},
    {"action": "assert_table_size", "field": "Result", "rows": 2, "columns": 7},
    {"action": "assert_cell", "field": "Result", "cell": "R2C6", "equals": "100,00"},
    {
      "action": "assert_table",
      "field": "Result",
      "equals": [
        ["Дата отгрузки", "Номер", "Дата заказа", "Организация", "Контрагент", "Сумма", "Валюта"],
        ["05.11.2026", "000001", "04.11.2026", "Тестовая организация", "Тестовый покупатель", "100,00", "RUB"]
      ]
    }
  ]
}
```

```bash
edt-bridge-mcp test-form \
  --platform-bin /opt/1cv8/x86_64/8.5.1.1529 \
  --test-infobase /srv/test-bases/orders --scope fixture \
  --erf /srv/artifacts/PlannedShipments.erf \
  --form ExternalReport.PlannedShipments.Form.Main \
  --form-title 'Плановые отгрузки' --user Tester \
  --scenario /srv/scenarios/shipments.json \
  --output-dir /srv/results/shipments-01 --timeout 300
```

Действие `assert_table` сравнивает фактический текст ячеек и порядок строк. Нажатие
"Сформировать" или сообщение о завершении не заменяют проверку содержимого отчета.

## Проверка установленного расширения и сохраненных значений

Подготовить документ, установить расширение и записать исходные значения контрольного
набора. В примере ожидается предупреждение, если плановая дата отгрузки раньше даты заказа,
затем сохраненные даты проверяются в другой сессии. Сохранить сценарий
в `/srv/scenarios/order.json`:

```json
{
  "version": 1,
  "steps": [
    {"action": "assert_field", "field": "OrderDate", "equals": "06.11.2026 12:00:00"},
    {"action": "input", "field": "PlannedShipmentDate", "text": "05.11.2026"},
    {"action": "click", "button": "Записать"},
    {"action": "assert_messages", "text": "Плановая дата отгрузки раньше даты заказа.", "count": 1},
    {"action": "assert_field", "field": "PlannedShipmentDate", "equals": "05.11.2026"}
  ],
  "reopen": [
    {"action": "assert_field", "field": "OrderDate", "equals": "06.11.2026 12:00:00"},
    {"action": "assert_field", "field": "PlannedShipmentDate", "equals": "05.11.2026"}
  ]
}
```

```bash
edt-bridge-mcp test-form \
  --platform-bin /opt/1cv8/x86_64/8.5.1.1529 \
  --test-infobase /srv/test-bases/orders --scope application \
  --navigation-link 'e1cib/data/Document.CustomerOrder?ref=0123456789abcdef0123456789abcdef' \
  --form Document.CustomerOrder.Form.Main \
  --form-title 'Заказ покупателя 000001' --user Tester \
  --scenario /srv/scenarios/order.json \
  --output-dir /srv/results/order-01 --timeout 300
```

После окончания первой фазы `reopen` запускает новые сессии TestClient и TestManager
для той же базы, пользователя и цели. Допустимы только `assert_field`, `assert_cell`,
`assert_table` и `assert_table_size`. Отредактированная форма не используется повторно,
запись вместо сценария не выполняется. При открытии формы по-прежнему работают ее
прикладные обработчики.

Для проверки штатного отказа в записи подготовить данные, которые вызывают проверку
самой конфигурации. Попытаться изменить данные, проверить штатное сообщение отказа,
а в `reopen` ожидать исходные сохраненные значения. Включить реквизит, который фактически
менялся в первой фазе, чтобы отсутствие записи не выглядело успешным обновлением.
Проверка поля в первой фазе читает открытую форму и не доказывает сохранение данных.
Для случаев без дополнительного предупреждения расширения использовать отдельный
запуск с `assert_messages` и `count: 0`.

Если при отказе открывается стандартный диалог ошибки платформы, добавить к шагу
`click` поле `expect_error_dialog` с точным текстом сообщения. Например:

```json
{"action": "click", "button": "Записать", "expect_error_dialog": "Не удалось записать заказ."}
```

Менеджер сверяет текст `ErrorInfo` формы `ErrorWindow` перед нажатием ее кнопки `OK`.
При другом тексте проверка завершается неуспешно; диалог остается открытым для снимка.
Фактический текст и результат закрытия записываются в отчет. Параметр не обрабатывает
другие диалоги и не заменяет проверки сообщений и сохраненных данных.

Если команда отвечает окном предупреждения (`ПоказатьПредупреждение`), а не сообщением,
добавить к шагу `click` поле `expect_warning` с точным текстом окна:

```json
{"action": "click", "button_name": "ФормаЗаписать", "expect_warning": "Проверьте дату отгрузки."}
```

Менеджер находит окно поверх формы – системную форму `MessageBox`, которая получает номер
(`MessageBox85`), если окно открыла форма объекта. Он сверяет текст надписи `Message`, нажимает
`OK` и переходит к следующему шагу, поэтому предупреждение в `ПередЗаписью` не мешает проверить
записанные значения. При другом тексте проверка завершается `assertion_failed` с фактическим
текстом, а нажатие без окна предупреждения завершает шаг ошибкой. Шаг ждет одно окно:
`expect_error_dialog` и `expect_warning` взаимоисключающие.

## Существующая проверка одной кнопки

Профиль EPF по-прежнему принимает `--epf`, `--button` и `--expect-message`. После нажатия
число вхождений ожидаемого сообщения должно увеличиться. Без `--expect-message`
результат – `command_observed`, `ok=false`, код возврата 2. Для точного числа сообщений,
проверки их отсутствия или проверки данных использовать `--scenario`. Параметры
`--button` и `--scenario` взаимоисключающие; `--expect-message` со сценарием не применяется.

## Результаты

Если менеджер тестирования не подключился при запуске, `test-form` повторяет
попытки в пределах оставшегося времени `--timeout`, пока порт принадлежит тому же
клиенту. Повторы прекращаются при подключении или при ошибке доступа либо
лицензирования. Поле `connectAttempts` показывает число попыток в фазе.

Команда печатает JSON и записывает `result.json`, если каталог результата уже создан.
Результат сценария содержит `phases`, наблюдения в `interaction` каждой фазы и проверки
`assertions` с полями `expected`, `actual`, `ok`. Для сообщений также записываются
`baselineCount` (сколько раз текст был в панели до нажатия) и `panel`. Снимки сохраняются в `steps/screenshot.png` и, если вторая фаза выполнена,
в `reopen/screenshot.png`. Проверка одной кнопки использует `screenshot.png` в каталоге
результата. Пути к снимкам указаны в JSON.

| Результат | Значение |
| --- | --- |
| `scenario_completed`, `ok=true` | Все проверки во всех запрошенных фазах прошли; обязательные снимки получены. |
| `assertion_failed` | Фактическое значение или число сообщений отличается от ожидаемого. |
| `message_baseline_not_empty` | Панель сообщений не изменилась, а ожидаемый текст в ней уже был; записало ли нажатие его снова, не установлено. |
| `scenario_error`, `command_error` | Не удалось выполнить действие, найти элемент или завершить операцию платформы. |
| `unexpected_dialog` | Нажатие открыло поверх формы окно предупреждения или вопроса, которого шаг не ждал. Поле `dialog` содержит его вид `kind` (`warning`, `question`), текст `text` и видимые кнопки `buttons`; сценарий на этом останавливается, вопрос остается без ответа, а вызывающая сторона решает, допустим ли такой ответ. |
| `dependency_missing`, `license_unavailable`, `access_denied`, `setup_failed` | Окружение или права не позволяют выполнить проверку. |
| `client_environment` | Ни один `conf.cfg`, который читает клиент, не задает `DisableUnsafeActionProtection`, и клиент остановился бы на предупреждении безопасности; см. `clientEnvironment` и [Подготовку окружения](#подготовка-окружения). |
| `timeout` | Истек общий предел времени. Записанный этап и доступный снимок показывают место остановки. |
| `screenshot_failed` | Наблюдения прошли проверки, но обязательный снимок не получен. |

`eventLog.errors` перечисляет ошибки, которые платформа записала в журнал регистрации
тестовой базы за время проверки. Ошибка серверного вызова показывает клиенту только окно
ошибки, а журнал сохраняет описание: у каждой записи есть `message`, `module` и `line` места,
где возникла ошибка, `stack` с вызывающими строками, `event` (`_$PerformError$_` для ошибки
выполнения) и `time`. Ошибка, перехваченная в `Попытка`, в журнал не попадает и в списке
отсутствует. Журнал читается в текстовом формате платформы (`1Cv8Log/*.lgf`, `*.lgp`); для
базы, где он хранится в SQLite (`1Cv8.lgd`), `eventLog.read` равно `false` с пояснением.

Если `field` шага не находит ни одного поля или находит несколько, результат содержит
`observedFields`: поля и таблицы формы, которые видит тестовый клиент, каждое с `name`,
`title`, `kind`, `visible` и `enabled`, сначала видимые, не больше 200, и `total`. Поля,
которые форма создает при открытии, например быстрые настройки штатной формы отчета, больше
нигде не названы.

Другие диагностические статусы, в том числе ошибки выбора формы и менеджера тестирования,
сохраняются в JSON. Код возврата 0 означает успех, 1 – ошибку при проверке входных данных,
2 – ошибку на более позднем этапе или неподтвержденный результат. Поля `status`, `stage`
и данные фаз позволяют отличить ошибку прикладного сценария от неготовности окружения.
Нажатие кнопки без успешной проверки результата не считается пройденным сценарием.
